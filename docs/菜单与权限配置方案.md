# 菜单与权限配置（第一版）

## 范围

采用“用户绑定角色、角色绑定菜单”的模型。第一版提供配置页面、接口协议和 Mock 数据，不执行当前登录用户的导航过滤、路由拦截或接口鉴权。

- 系统设置 → 菜单配置：`/admin/menus`，树形列表默认全部收起、支持逐行展开/收起、搜索、状态筛选，抽屉新增和编辑、删除。
- 系统设置 → 权限配置：`/admin/permissions`，角色新增和编辑、菜单树勾选、删除角色、用户分配多个角色、有效菜单预览。
- 页面路径支持选择已有路由或输入新路径。配置路径不会自动创建 React 页面，业务页面仍需在前端实现。

## 数据模型和规则

| 实体 | 主要字段                                                                             |
| ---- | ------------------------------------------------------------------------------------ |
| 菜单 | id、parentId、name、code、type（directory/page）、path、icon、sort、enabled、visible |
| 角色 | id、name、code、description、enabled、menuIds                                        |
| 用户 | id、name、username、roleIds                                                          |

角色存储页面菜单 ID；目录用于分组，通过勾选目录批量选择下级页面，目录展示由下级授权推导。空目录不作为独立授权资源。

多个角色的页面权限取并集。停用角色不参与权限计算；停用目录时，其全部下级页面也排除在有效菜单之外。隐藏菜单仍可被授权，隐藏仅用于导航展示。

菜单标识、页面路径和角色标识各自唯一。禁止目录移动到自身或后代、页面下挂子菜单、存在子菜单的目录直接转页面。删除菜单前必须移除下级和角色绑定；删除角色前必须解除用户绑定。更新菜单不会改变菜单 ID，因此角色绑定得以保留。

## 实现分层

- `mock/systemConfig.ts`：全部演示用户、角色、初始菜单和模拟接口，以及 Mock 专用的 Zod 结构校验与关联校验；初始菜单由当前路由生成。
- `src/services/systemConfig.ts`：页面使用的接口调用，沿用统一请求封装。
- `src/models/systemConfig.ts`：共享服务端配置状态、加载和保存状态。
- `src/types/systemConfig.ts`：菜单、角色、用户及接口配置的类型定义。
- `src/utils/menu.ts`：前端仍需使用的树形构建、后代查找和有效菜单计算，不依赖 Mock 或 Zod。
- `src/pages/SystemSettings/MenuConfig/pageOptions.ts`：从前端路由提取页面路径候选项，仅供菜单配置表单使用。

Mock 由 Umi 自动扫描项目根目录下的 `mock/` 注册。数据只保存在开发服务进程的内存中，同一开发服务下各页面共享，刷新浏览器保留；重启开发服务或重新加载 Mock 模块后恢复初始数据。不使用 localStorage。生产构建不提供这些 Mock 接口，需对接真实后端。

## 接口协议

| 方法   | 地址                        | 用途                                      |
| ------ | --------------------------- | ----------------------------------------- |
| GET    | /api/system/config          | 获取菜单、角色和用户关系                  |
| POST   | /api/system/menus           | 新增菜单                                  |
| PUT    | /api/system/menus/:id       | 更新菜单                                  |
| DELETE | /api/system/menus/:id       | 删除菜单                                  |
| POST   | /api/system/roles           | 新增角色及菜单绑定                        |
| PUT    | /api/system/roles/:id       | 更新角色及菜单绑定                        |
| DELETE | /api/system/roles/:id       | 删除角色                                  |
| PUT    | /api/system/users/:id/roles | 更新用户角色，body 为 `{ "roleIds": [] }` |

菜单、角色写接口接收完整记录。新增 ID 由服务端生成；现有路由作为初始菜单 ID 时包含 `/`，service 使用 URL 编码。

成功统一返回 `{ "success": true, "data": { "version": 1, "menus": [], "roles": [], "users": [] } }`；写接口返回更新后的完整配置。失败返回非 2xx HTTP 状态与 `{ "success": false, "message": "错误原因" }`。Mock 在校验成功后整体提交，失败不会部分修改配置。

## 后续后端落地

数据库可使用 `menu`、`role`、`user`、`role_menu`、`user_role` 五张表，用户复用现有账号体系。后端校验菜单树完整性、唯一标识及关联关系，授权配置的写接口本身也必须受保护。

后续登录时由后端返回当前用户的有效菜单，在 `src/access.ts` 关联路由访问规则，在布局中生成可见菜单。未登录走登录页，无权限显示 403；无权访问当前页或默认页时进入首个可访问页面。实际业务接口仍需独立执行服务端鉴权。

后端若以分别读取菜单、角色、用户的接口替代全量配置接口，只需相应调整 service 和 model；页面不依赖 Mock 实现。
